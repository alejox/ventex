# Architecture (mandatory layers)

**Components never perform I/O directly.** All features follow:

`components/app` → `stores/<feature>.store.ts` (Zustand) → `services/<feature>.service.ts` (I/O)

- **Components**: read stores via granular selectors (`useXStore((s) => s.field)`); UI-only state in `useState`. No `axios`/`supabase`/`fetch`.
- **Stores**: state + async actions delegating to services. No JSX, no direct I/O.
- **Services**: the only layer doing I/O. Supabase client for app data (RLS preserved); `axios` (`services/http.ts`) for external APIs only.

Reference slice: `services/inventory.service.ts` → `stores/inventory.store.ts` → `app/dashboard/inventory/page.tsx`.

# Tenancy: key off `get_effective_user_id()`, NOT `auth.uid()`

Workers (`profiles.is_worker`) log in with their **own** auth account, but their tenant is the owner's. Every RLS policy, trigger, and RPC uses `public.get_effective_user_id()` (resolves to the owner's `workspace_id` for workers, `auth.uid()` otherwise). **Any new tenant-scoped table, policy, default, or RPC must key off `get_effective_user_id()`** — using bare `auth.uid()` silently attributes worker writes to the wrong tenant. See `supabase/migrations/20260715000000_add_worker_role.sql` and `20260730230000_align_tenant_insert_defaults.sql` (which enforces this as the `user_id` column default).

- **Client factories** — pick by context:
  - `utils/supabase/client.ts` → `createClient()` — Client Components (browser)
  - `utils/supabase/server.ts` → `await createClient()` — Server Components / Server Actions / route handlers (**async**)
  - `utils/supabase/proxy.ts` → `updateSession(request)` — only inside `proxy.ts`
  - `utils/supabase/admin.ts` → `createAdminClient()` — service-role key, **bypasses RLS**; only for privileged server-side work (admin/reseller), never exposed to clients. Requires `SUPABASE_SERVICE_ROLE_KEY`.
- **Migrations**: apply via MCP `apply_migration`, then save the `.sql` to `supabase/migrations/` to keep repo and remote in sync. After schema changes, regenerate `utils/supabase/database.types.ts` (MCP `generate_typescript_types`).
- **`create_sale` RPC**: transactional sale creation (calculates totals server-side, applies IVA from `settings`, decrements stock, freezes staff commission). When `settings.require_active_shift` is enabled, employees without an open shift (`public.shifts`) are rejected inside the RPC and gated in the POS UI. The setting defaults to false and only the tenant owner can change it; owners are exempt. Shift model: `README-turnos.md`.
  - **Descuentos** (migración `20261006224422_create_sale_manual_discount_and_tendered.sql`): `p_discount_amount` sigue siendo el descuento TOTAL (manual + ofertas + premio de cortes + puntos). `p_manual_discount numeric default 0` declara qué parte puso el cajero en el DiscountModal: debe estar entre 0 y el total (`DESCUENTO_MANUAL_INVALIDO`), y si es > 0 y quien cobra es trabajador sin `worker_can('pos_discount')` la venta se rechaza con `SIN_PERMISO_DESCUENTO` (42501; `lib/errors.ts` lo traduce). Dueño y admin siempre pueden. La validación corre DESPUÉS de la idempotencia: el reintento de una venta ya registrada nunca falla por permisos. **Límite**: la separación manual/automático la declara el cliente (`CartLine.manualDiscount`, mantenido por `setLineDiscounts(…, source)`); el RPC no recalcula ofertas/premio/puntos (solo los usa como TOPE para el trabajador sin `pos_discount`, ver abajo).
  - **Por línea**: cada item de `p_items` puede traer `discount_amount`; se guarda en `sale_items.discount_amount` (CHECK `0 ≤ descuento ≤ line_total`) y, si viene, la suma tiene que cuadrar con `p_discount_amount` ±0,01 (`DESCUENTO_LINEAS_NO_CUADRA`). Sin la clave (cliente viejo, cola offline) las líneas quedan en 0 y el descuento solo existe a nivel venta, como antes. `checkoutDiscounts` (`lib/sale-discounts.ts`) redondea por línea sin perder la suma y omite el desglose si alguna línea quedó con más descuento que lo que vale.
  - **Efectivo recibido**: `p_amount_tendered numeric default null` → `sales.amount_tendered` (solo efectivo sin split). La reimpresión (`fetchSaleReceiptAmounts` + `buildReceiptFromSale`) imprime recibido/cambio y el descuento por línea solo si cuadra con el de la venta; tolera que las columnas no existan.
  - **Compatibilidad**: los parámetros nuevos van al final con default, y la firma vieja se dropea en la misma migración (si conviviera, toda llamada sería ambigua). El cliente solo los manda si tienen valor y, ante `PGRST202`, reintenta con la firma vieja (`createSaleWithFallback`, mismo patrón que `voidSale`) — así funciona antes y después de aplicar la migración, incluida la cola offline. Prueba sin persistir: `supabase/manual-tests/20261006224422_create_sale_manual_discount.rollback.sql`.
  - **Tope de descuento (`20261007100000`)**: para un trabajador SIN `worker_can('pos_discount')`, `create_sale` exige que todo `p_discount_amount` lo justifiquen ofertas vigentes (la mejor por línea, espejo de `offerDiscountsFor`, ventana de fechas con holgura UTC-12..UTC+14) + el premio de cortes alcanzado (progreso PREVIO a la venta, topado en el servicio que cuenta más caro) + `loyalty_points × points_value`, ±0,01; si no, `DESCUENTO_NO_JUSTIFICADO` (42501). Dueño/admin y trabajadores con `pos_discount`: sin tope. Si cambias `offerDiscountsFor`/`promoDiscountFor`, actualiza el espejo SQL.
  - **Comisión porcentual sobre el NETO**: `line_total − discount_amount` de la línea (IVA incluido); sin desglose por línea, el descuento de la venta se prorratea por `line_total`. Las fijas no cambian.
  - `p_customer_id` tiene que ser del negocio (`CLIENTE_NO_ENCONTRADO`); el fiado bloquea al cliente `FOR UPDATE`.
- **`void_sale` devuelve jsonb** `{cash_refund, cash_refund_shift_id, cash_refund_unrecorded}` (`20261007100100`). La devolución en efectivo va al turno de la VENTA si sigue abierto, si no al turno abierto de quien anula; sin ninguno, el dueño/admin anula igual y la UI avisa que "no quedó registrada en ninguna caja". El trabajador sigue necesitando su turno. El movimiento lleva `cash_movements.kind = 'devolucion'` (el arqueo lo resta igual que los demás).
  - **Stock congelado y kardex (`20261007140000`)**: `sale_items.stock_qty_applied` guarda las unidades que la línea descontó (0 si no controla stock o es servicio); `void_sale` devuelve EXACTAMENTE eso y solo cae a la regla vieja (`tracks_stock`/`unit` actuales) cuando es NULL (ventas anteriores). `create_sale` escribe la salida de kardex (`inventory_movements` type `out`, `reference_type 'sale'`), espejo de la entrada `sale_void` de la anulación. Las dos funciones bloquean los productos en orden de id antes de tocarlos (mismo orden que `replace_purchase_invoice_items`) para no cruzarse en deadlocks.
  - **Turno y cierre**: `create_sale`/`void_sale` leen el turno abierto con `FOR SHARE`; `close_shift` lo toma `FOR UPDATE`. Una venta concurrente con un cierre espera y, si el turno quedó cerrado, cae en `CONTEXTO_DE_TRABAJO_CAMBIO` / "Debes abrir turno". No quites el lock: sin él, la venta queda en un turno que ningún arqueo cuenta.
  - **Método de pago**: `create_sale` solo acepta `efectivo|tarjeta|transferencia|credito` (venta y splits; `METODO_PAGO_INVALIDO`, 22023) y `sales_payment_method_check` cierra la tabla (+ `split`, que pone la función).
  - **Totales del POS**: `computeTotals` redondea cada línea a centavos con `lineTotalCents` (cantidad a 3 decimales, mitad hacia arriba), igual que `line_total` en la base. El IVA del POS (`taxRate`/`includeTax`) se relee al volver el foco y antes de cobrar (`refreshPosConfig`); si el total cambia, el cobro se corta para que el cajero lo revise. `CheckoutInput` no lleva `includeTax`: el desglose lo decide `settings.include_tax` en la base.
  - **Un fiado ya abonado no se anula**: `credit_release_voided_sale` lanza `CREDITO_YA_ABONADO` si lo fiado supera el saldo actual (antes lo topaba en 0 y se comía los abonos).
  - **Premio de cortes y cola offline**: igual que los puntos, sin conexión el premio no se aplica y una venta con premio aplicado no se encola (`checkout({ rewardApplied })`): encolada, `redeem_promo` nunca correría.

# Promociones: el contador lo escribe la base, WhatsApp lo manda una persona

`customers.haircut_count` y `haircuts_since_reward` los mantienen TRIGGERS sobre `sale_items` (suma al vender) y `sales` (resta al anular) — nunca la app, que solo tiene GRANT de SELECT. Qué cuenta como corte sale de `settings.promo_service_ids` y arranca vacío: adivinar que el servicio llamado "Corte" es el que cuenta sería hardcodear el catálogo de un negocio en la base de todos.

- **No se tocó `create_sale`.** Es la función más crítica de la app —cobra, descuenta stock, congela comisiones, valida turnos— y sumarle contar cortes es la clase de cambio que rompe una venta por un feature de marketing. Los triggers son aditivos.
- **El envío es un enlace `wa.me`, no la API de Meta.** Abre WhatsApp con el mensaje escrito y lo manda una persona desde la ficha del cliente. Sin BSP, sin plantillas aprobadas, sin costo por conversación. Consecuencia: el texto es libre (con la API habría que ceñirse a una plantilla aprobada) y no hay estado de entrega que registrar.
- **Dos contadores con roles distintos**: `haircut_count` es de por vida (el número de la relación, `{total}` en el mensaje) y `haircuts_since_reward` es el PROGRESO hacia el premio (`{cortes}`). El premio sale del progreso, nunca del histórico.
- **El corte que paga el premio NO cuenta para el premio siguiente.** El trigger suma todo corte sin preguntar quién pagó, y el canje corre después de registrar la venta: entre esas dos piezas se colaba el corte gratis (progreso 10 → venta gratis → 11 → canje 11−10 = **1**), dejando al cliente un crédito por un corte que nunca pagó. Medidos antes de `20260824120000`: los 5 canjes de la base tenían `progress_before = 11` y los 4 del POS se cobraron en **$0.00**. La señal es el descuento contra el precio de la unidad, no `reward_kind` — eso cubre de una `gratis`, `porcentaje` de 100 y un `monto` que iguala el precio, y deja afuera el descuento parcial, donde el cliente puso la diferencia. Se descuenta ANTES de elegir el hito: con hitos de 10 y 11, el corte gratis entregaba el de 11. `promo_redemptions.rewarded_haircuts` lo CONGELA porque `recalc_haircut_counts()` tiene que reconstruir el mismo número cuando los precios ya cambiaron.
- **El canje NO pone el progreso en cero: consume el umbral entregado y el resto arranca el conteo siguiente.** Quien llegó a 11 PAGANDO y canjea uno de 10 queda en 1 — ese corte lo hizo y lo pagó, y ponerlo en cero es cobrarle por haber vuelto antes de pasar por el mostrador. El carry-over vale para lo que pagó el cliente, nunca para lo que pagó el premio (bullet de arriba). Con varios hitos descuenta el ENTREGADO, no el más bajo: progreso 21 con hitos de 10 y 20 entrega el de 20 y deja 1; descontar 10 dejaría 11 y regalaría un segundo premio al toque. La cuenta autoritativa es `redeem_promo`, que devuelve `progress_after`; `progressAfterRedeem` la espeja (pura, testeada) solo para poder AVISARLO en el modal antes de confirmar. **No prometas "vuelve a cero"** en copy nueva: el número lo dice la base.
- **`redeem_promo(customer)`** registra el canje en `promo_redemptions` —con umbral y premio CONGELADOS— y reinicia el progreso, todo en una transacción: sueltas, un fallo en el reinicio deja al cliente con el premio entregado y el contador intacto para reclamarlo otra vez. Requiere `worker_can('pos')`, no dueño: se canjea en el mostrador.
- **El POS aplica el descuento**, pero solo si el premio declara su forma: `promo_milestones.reward_kind` ∈ `texto|gratis|porcentaje|monto`. `texto` es el default y existe a propósito — "una cerveza" no se descuenta de la cuenta. `promoDiscountFor` (puro, testeado) elige la línea MÁS CARA de las que cuentan y descuenta UNA unidad, topado en su precio.
- **Una venta de total 0 NO tiene fila en `sale_payments`.** Con el premio al 100% el total queda en cero y `create_sale` reventaba contra `sale_payments_amount_check` (`amount > 0`), tirando abajo la venta entera. No se aflojó el CHECK —un pago de cero no es un pago, y habilitarlo dejaría entrar splits vacíos que la misma función rechaza—: simplemente no se inserta.
- **Anular la venta devuelve el premio.** `promo_redemptions.sale_id` ata el canje a su venta y `progress_before` guarda el progreso previo, que es lo único que permite reconstruirlo (el progreso es acumulado y no se deduce hacia atrás desde cero). `undo_haircut_count` restituye ese valor ANTES de descontar los cortes de la venta: al revés, la resta caería sobre un cero y `greatest(...,0)` se la comería.
- **Aplicar es explícito**, con un botón: descontar solo sería regalar plata sin que nadie lo decida. Y el canje corre DESPUÉS de que la venta quedó registrada — al revés, un cobro fallido le quema el premio al cliente por una venta que no existió.
- `availableReward` devuelve el hito más alto que el progreso ALCANZÓ O PASÓ; no exige coincidencia exacta, porque perder el premio de 10 por llegar a 12 es la forma más rápida de que el cliente no vuelva.
- **Dos mensajes, dos momentos.** La visita del canje NO manda el mensaje del contador: ahí el progreso quedó en 0 y "Ya llevas 0 cortes" es lo último que se le manda a quien acaba de llevarse el premio. `renderRedeemMessage` es el de esa visita; `renderPromoMessage` vuelve a ser el de la siguiente. Se dispara por **dos** caminos, y los dos hacen falta: el POS pasa el premio entregado (lo sabe, `redeemPromo` se lo devolvió), y `renderPromoMessage` cae solo al mensaje de canje cuando **`cortes === 0` Y `total > 0`**. La segunda condición ES la regla del negocio —"la promoción no se puede canjear si no hay cortes"— puesta en código: hay DOS ceros distintos, el del que acaba de canjear y el del que nunca pisó el local, y `total` (histórico de por vida) es lo único que los separa. Sin él, a un cliente nuevo se le anuncia un premio que no existió. **El mensaje sale de TRES pantallas** (POS, Clientes, Promociones): arreglar solo el POS deja el problema vivo en las otras dos, que es exactamente lo que pasó.
- **Trampa del mensaje**: el editor precarga el texto por defecto y guardarlo lo CONGELA, así que mejorar el default después no alcanza a quien ya guardó. Por eso Ajustes avisa si hay hitos y el mensaje no incluye `{premio}`. **Corolario**: toda mejora al texto del premio va DENTRO de `renderPromoMessage`, envolviendo la variable — es lo único que alcanza a las plantillas que ya están en la base. **El hito AVISA, el hito + 1 CANJEA — y son dos palabras distintas.** Con un hito de 10, el corte 10 es el último que el cliente PAGA y el 11 es el premio. `{premio}` no renderea el nombre pelado ("…Ya llevás 10 cortes. Corte gratis" deja el premio colgando): lo anuncia con `PROMO_ACHIEVED_LEAD`, que dice **"te espera en tu próxima visita"** y NUNCA "canjeaste". Decir "¡Completaste tu promoción!" en el hito —como decía— se lee como si ya se lo hubiera llevado, un corte antes de que pase, y desde afuera parece que el sistema dispara la promo corrida cuando lo único corrido es el texto. Los valores se insertan con función de reemplazo, no como string: `String.replace` interpreta `$&` y `$'`, y el premio lo escribe una persona. **Con 1 la palabra que sigue al contador va en singular** (`singularizarJuntoAl`): "Ya llevas 1 cortes" pasa en CADA reinicio de ciclo. Se corrige sobre la PLANTILLA y solo en la palabra pegada al token —la palabra la escribe el negocio, no la variable—, así que otro "1 algo" del mensaje queda intacto y 11/21 siguen en plural.
- `recalc_haircut_counts()` reconstruye los contadores desde el histórico. Es el backfill Y la red de seguridad si cambian qué servicios cuentan. **Los dos contadores se reconstruyen distinto**: el histórico es la suma de todo, pero el progreso son los cortes POSTERIORES al último canje más el excedente que ese canje no consumió, menos su `rewarded_haircuts`. Asignarle el histórico al progreso —lo que hacía hasta `20260815260000`— le devuelve al cliente un premio ya cobrado, y cuanto más fiel el cliente más grande el regalo. La venta que consumió el premio queda fuera del conteo: el canje corre después de registrarla, así que sus cortes ya están dentro de `progress_before`.
- `settings` se crea PEREZOSAMENTE: un negocio que nunca abrió Ajustes no tiene fila. Todo lo que escriba ahí tiene que leer-e-insertar-o-actualizar (ver `savePromoConfig`).
- La lógica pura —qué hito aplica, cómo se arma el mensaje, cómo se normaliza el teléfono— vive en `services/promos.service.ts` y está testeada sin base (`tests/promos.test.ts`).
- **El reporte de cortes (`/dashboard/staff/cortes`) es una métrica APARTE de las comisiones, no una vista de ellas.** Comisiones contesta "¿cuánto le debo?" (pesos, congelados al vender, solo de lo que comisiona); Cortes contesta "¿quién trabaja más?" (cabezas, incluidos los cortes sin comisión, y no cambia si mañana se ajusta un porcentaje). Cruzarlas daría un número que no contesta bien ninguna de las dos. Cuenta lo MISMO que el contador del cliente —`settings.promo_service_ids`—, así que sin servicios elegidos sale vacío, y eso es correcto: "corte" es una definición del negocio, no del código. La agregación (`aggregateHaircuts`) es pura y está testeada (`tests/haircuts-by-staff.test.ts`); el rango es abierto porque comparar períodos ES el uso.

# Ofertas de tienda: dominio separado del contador de cortes

`tienda` no tiene servicios de mostrador, así que el motor de fidelización de arriba (contador de cortes, hitos, WhatsApp) no le sirve de nada — y mostrárselo era justo el bug que esta feature cierra. `product_offers` es su propia tabla, sus propias pantallas y su propia función de precio; no comparte una sola fila ni una sola línea de código con `promo_milestones`/`promo_redemptions`.

- **La pestaña "Promociones" no se duplicó, se RAMIFICÓ.** `usesHaircutPromos(businessType, modules)` en `config/business.ts` es la única fuente de verdad — literalmente reusa `visibleNavItems(...).some(i => i.id === "promociones")`, el mismo cálculo que ya decidía si el ítem de sidebar existe. `SettingsTabs.tsx` y `/dashboard/settings/promociones/page.tsx` la consultan para decidir qué mostrar (o si mostrar la pestaña siquiera). Para salón/lavaautos/servicios/escuela el resultado es idéntico a como era: siempre tuvieron el módulo `services` encendido por defecto.
- **Tres formas de descuento, una función pura.** `offerDiscountsFor(cart, offers, today)` en `services/offers.service.ts` prueba cada oferta vigente contra cada línea y se queda con la de MAYOR descuento cuando varias alcanzan (nunca se suman). `amount` es POR UNIDAD —escala con la cantidad, tal como un cajero lo esperaría de "$2.000 de descuento"— y siempre queda topado al valor total de la línea. `buy_n_pay_m` se salta cantidades fraccionarias a propósito: "lleva 3 paga 2" no tiene una respuesta razonable sobre 2,4 kg de algo.
- **`today` viaja como string, nunca como `Date`.** Es lo único que hace testeable la ventana de fechas sin mockear el reloj; `todayLocal()` (el único lugar que sí lee `Date`) usa la fecha LOCAL del dispositivo — con UTC, un negocio en Colombia vería sus ofertas cortarse a las 19:00 en vez de a medianoche.
- **Una línea con descuento manual nunca se pisa.** `offerDiscountsFor` se salta cualquier línea con `discountAmount > 0` que no traiga `offerId`: es la señal de "esto lo tocó el cajero", y una oferta no le gana a una decisión humana. Una línea que SÍ trae `offerId` (de una pasada automática anterior) se recalcula sin problema — es lo que permite reaccionar a un cambio de cantidad sin confundirlo con lo manual.
- **Se aplica desde el store, nunca desde un efecto de React.** `pos.store.ts` llama a `get().recomputeOffers()` al final de cada acción que muta el carrito (agregar, cambiar cantidad, pasar a caja, asignar precio abierto, incluso un descuento manual que hay que limpiar de oferta). Un `useEffect` que reaccionara a `cart` y volviera a hacer `setState` sobre el mismo carrito es exactamente el patrón que dispara `react-hooks/set-state-in-effect`; resolverlo en el store lo evita de raíz.
- **"Quitar" una oferta es por sesión de venta, no para siempre.** `SaleTab.removedOfferKeys` recuerda qué líneas el cajero sacó a mano PARA ESTA VENTA; sin esto, el siguiente cambio de carrito la volvería a aplicar sola, porque nada más distingue "nunca calificó" de "calificó y se sacó a propósito". Se limpia cuando la línea sale del carrito o cuando se cobra: en la venta siguiente la oferta vuelve a ofrecerse.
- **Mismo split de permisos que `promo_milestones`.** Leer (`workspace_product_offers_read`) es de cualquiera del negocio —el cajero necesita saber qué aplica—; escribir (`workspace_product_offers_write`) exige `is_tenant_owner()`. `OffersManager` (Ajustes → Promociones, rama `tienda`) oculta el formulario a un worker en el cliente, pero la RLS es la que de verdad lo impide.
- **No se tocó `create_sale`.** El descuento de una oferta viaja por el mismo canal que ya usaba el descuento manual y el premio de cortes: `CartLine.discountAmount`, sumado a `p_discount_amount` al cobrar. Es la misma razón por la que el motor de cortes tampoco toca esa función — ver la sección de arriba.

# Puntos de tienda: LEDGER, no un contador — y tampoco se tocó `create_sale`

Fase 2 de las promociones de tienda (la fase 1 es "Ofertas de tienda", arriba). El cliente gana puntos comprando y los canjea como descuento en una venta futura. Mismo argumento de siempre para no meterle esto a `create_sale`: es la función más crítica de la app, y otorgar/canjear puntos es un feature de marketing — ver `earn_loyalty_points`/`reverse_loyalty_points`/`redeem_loyalty_points` en `supabase/migrations/20260927010000_loyalty_points.sql`.

- **Por qué un ledger y no un contador como `haircut_count`.** El contador de cortes solo necesita SUMAR (un trigger sobre `sale_items`) y RESTAR-A-CERO al canjear; nunca hace falta reconstruir un movimiento puntual. Los puntos sí: un canje se ata a UNA venta y anular esa venta tiene que revertir EXACTAMENTE lo que ganó Y lo que canjeó, sin tocar ninguna otra. `loyalty_points_ledger` (una fila por movimiento: `earn`/`redeem`/`reverse`/`adjust`, el último reservado y sin nada que lo escriba todavía) es la fuente de verdad; `customers.loyalty_points` es un CACHÉ derivado, sumado por el trigger `apply_loyalty_ledger_entry` en cada INSERT del ledger — mismo patrón de protección que `haircut_count` (columna con `GRANT SELECT` nada más), pero acá con auditoría completa en vez de un solo número.
- **El otorgamiento se engancha al UPDATE que fija `sales.total`, no al INSERT.** `create_sale` inserta la venta con `total = 0` y la corrige en un UPDATE posterior, ya con el descuento (ofertas + manual + puntos) y el IVA aplicados — ver el cuerpo actual de la función. `earn_loyalty_points` dispara en `AFTER UPDATE OF subtotal, tax_amount, total`, así que calcula puntos sobre el NETO final, nunca sobre cero. Esto además hace que funcione gratis para una venta que llega por la cola offline: llega tarde, pero pasa por el mismo `create_sale` y por lo tanto por el mismo UPDATE.
- **Se gana sobre lo que el cliente terminó pagando** (`sales.total`, después de ofertas, descuento manual Y de los puntos que él mismo canjeó en esa venta), solo si tiene cliente asignado, solo para `tienda` con `settings.points_enabled` y una tasa (`points_peso_per_point`) configurada. Redondeo hacia abajo (`floor`): regalar el punto de más sería inventar plata que la base nunca otorgó.
- **Todo es idempotente por índices únicos parciales, no por lógica de aplicación.** `loyalty_ledger_one_earn_per_sale`/`_one_redeem_per_sale` (únicos en `sale_id` filtrando por `kind`) hacen que un reintento del mismo UPDATE o del mismo canje no duplique nada — el trigger y el RPC usan `ON CONFLICT ... DO NOTHING` contra esos mismos índices. `loyalty_ledger_one_reverse_per_entry` (único en `reverses_id`) impide que anular una venta dos veces la reverse dos veces.
- **Canjear es un RPC que corre DESPUÉS del cobro**, atado al `sale_id` — mismo motivo que `redeem_promo`: si el cobro fallara, un canje adelantado le habría quemado los puntos al cliente por una venta que no existió. `redeem_loyalty_points(p_sale_id, p_points)` exige `worker_can('pos')`, topa contra el saldo (`customers.loyalty_points`, con `FOR UPDATE`) y es idempotente: reintentar el mismo canje devuelve el saldo vigente sin descontar dos veces. Lo que NO valida server-side es que `p_points * points_value` tenga sentido contra el total de la venta — mismo modelo de confianza que el descuento manual de siempre.
- **El descuento en el POS se reparte entre líneas, nunca reemplaza a una oferta sin avisar.** `loyaltyLineDiscounts(cart, pointsValue, points)` en `services/loyalty.service.ts` calcula el REMANENTE de cada línea (`linePrice*qty - discountAmount` actual, que ya incluye lo que haya puesto una oferta o un descuento manual) y reparte empezando por la de MÁS remanente, saturando cada una antes de seguir — así el descuento de los puntos se aplica DESPUÉS de las ofertas y sobre lo que queda, nunca por encima de lo que una línea vale. Viaja por `setLineDiscounts`, el mismo mecanismo que ya usa el premio de cortes en salón.
  - **Límite conocido y aceptado**: `setLineDiscounts` limpia `offerId`/`offerName` de toda línea que toca (es el mismo campo el que usan las ofertas automáticas y cualquier descuento manual, y no hay forma de tener las dos cosas a la vez). Si los puntos tocan una línea que ya traía una oferta, el número final sigue siendo correcto pero la etiqueta de "por qué bajó el precio" se pierde, y "Quitar" el canje NO resucita la oferta ahí — revierte la línea a su descuento ANTERIOR exacto (gracias al snapshot `previous` que guarda el POS al aplicar), pero con la oferta ya sin nombre. Es exactamente el mismo trato que ya tiene hoy cualquier descuento manual sobre una línea con oferta.
- **Sin conexión no se puede canjear, a propósito — no se inventó un canje diferido.** `useOnlineStatus()` (`lib/useOnlineStatus.ts`) deshabilita el control de canje en el POS cuando `navigator.onLine` es `false`: un canje necesita el `sale_id` real que el servidor recién asigna, y una venta offline se encola sin él. Si la conexión se cae justo entre aplicar el descuento y que `create_sale` responda (carrera rarísima, no la resuelve este diseño), la venta puede terminar encolada con el descuento ya adentro pero sin que el RPC de canje se haya llamado — el `checkout()` del POS solo intenta el canje cuando `outcome === "sold"`, nunca cuando `outcome === "queued"`.
- **Anular una venta revierte AMBOS lados.** El trigger `reverse_loyalty_points` (mismo `WHEN (old.status='completed' AND new.status='void')` que ya usan `sales_release_credit_on_void`/`schools_reconcile_on_void`) inserta una fila `reverse` por cada `earn`/`redeem` de esa venta, con el signo invertido. **Límite conocido y documentado en la migración**: si se anula una venta que otorgó puntos que el cliente YA gastó en una venta posterior, el saldo puede quedar transitoriamente NEGATIVO — a propósito no lleva `CHECK loyalty_points >= 0`, porque esa validación reventaría la anulación completa (corre en la misma transacción que `void_sale`), y frenar una anulación por un feature de marketing es peor que un número negativo que los próximos puntos ganados recomponen solos.
- **Ajustes → Promociones (rama `tienda`) tiene DOS gestores, no uno.** `OffersManager` (fase 1) y `LoyaltyManager` (fase 2, `enabled`/pesos-por-punto/valor-por-punto/mínimo para canjear) se muestran juntos, en ese orden. Mismo split de permisos que el resto: escribe el dueño, `settings` se crea perezosa (leer-e-insertar-o-actualizar, igual que `savePromoConfig`).
- **Clientes muestra saldo + historial, bajo demanda.** La ficha de un cliente (tienda con puntos activos) trae el saldo siempre, pero el historial del ledger se pide recién cuando el dueño toca "Ver movimientos" — una consulta más por cada apertura de ficha, en un negocio que ni siquiera es `tienda` la mayoría de las veces, no se justifica.

# Comisiones: el estado vive en la LÍNEA de venta

`sale_items.commission_amount` es el monto congelado al vender; `sale_items.commission_settlement_id` dice si ya se pagó. No hay total "pendiente" guardado en ninguna parte — se deriva sumando las líneas sin liquidación, y eso es lo que impide que el número y el detalle se contradigan.

- **Liquidar es un solo RPC y paga LO QUE SE VIO**: `settle_commissions(staff, from, to, from_ts, to_ts, método, pagado_el, excluidos[], p_item_ids[], p_expected_total)`. En una transacción suma las líneas pendientes (con `FOR UPDATE`), crea la fila en `commission_settlements`, crea el gasto en la categoría "Comisiones" (creándola si no existe) y estampa cada línea. **No repliques ninguno de esos pasos desde el cliente**: la idempotencia es que solo entra lo que tiene `commission_settlement_id IS NULL`. El modal manda los ids marcados y su suma (`settlementSelection`); el RPC bloquea SOLO esos y, si falta alguno o la suma no cuadra ±0,01, levanta `LIQUIDACION_CAMBIO` sin escribir nada y la UI recarga. Con `p_item_ids` NULL se comporta como antes (exclusión). `fetchStaffSales` pagina con `fetchAllRows`: una línea que no se ve no se paga.
- **El rango viaja en instantes, no en fechas.** `sales.created_at` es timestamptz y la base corre en UTC: cortar por `created_at::date` mete la venta de las 20:00 en Colombia en el día siguiente. `commissionPeriodOf()` (`services/staff.service.ts`) arma los dos formatos desde la zona del navegador; `from`/`to` son solo para imprimir.
- **El gasto generado no se edita ni se borra**: el trigger `expenses_guard_commission` lo rechaza. Para revertir se usa `void_commission_settlement`, que libera las líneas y borra el gasto (levanta `app.voiding_settlement` para pasar el guard).
- **Liquidar es del dueño**: los dos RPC revalidan `is_tenant_owner()`, igual que la policy de escritura de `expenses`.
- **Anular una venta ya liquidada NO reversa la comisión** — esa plata ya se entregó. Se avisa en tres lugares (confirmación de anulación en Ventas, chip en el historial, aviso en el comprobante); no lo conviertas en un bloqueo ni lo hagas cuadrar en silencio.
- **Pagar en efectivo descuenta del arqueo.** La liquidación inserta un `cash_movements` con `kind = 'comision'` — uno de los valores junto a `gasto`, `traslado` y `devolucion`. `comision` significa "descuadra la caja pero NO va al estado de resultados", porque el gasto ya lo creó la liquidación: reusar `kind = 'gasto'` contaría la misma plata dos veces. `close_shift` ya resta todos los movimientos del turno sin mirar el `kind`, así que el arqueo sale solo.
- **De qué cajón sale** lo decide `open_shift_for_commission(staff)`: primero el turno abierto de la persona a la que se le paga (vía `workspace_memberships.staff_id` del `membership_id` del turno — `profiles.staff_id` está vacío en producción y no sirve para esto), si no el único turno abierto del negocio. Con dos o más turnos abiertos y ninguno suyo devuelve NULL a propósito — adivinar metería un faltante en la caja de otro empleado. Sin turno abierto no hay movimiento y el gasto se crea igual. El efectivo sale del cajón abierto HOY aunque la fecha de pago sea anterior; el modal lo avisa.
- **Gasto de retiro de caja** (`expenses.cash_movement_id`): monto, fecha y vínculo quedan fijos (`GASTO_DE_RETIRO`); solo se editan descripción y categoría, y no se borra. Ningún gasto con `commission_settlement_id`/`cash_movement_id` se crea ni se vincula desde el cliente (`GASTO_VINCULADO`): `guard_commission_expense` es SECURITY INVOKER y distingue por `current_user` (los RPC SECURITY DEFINER corren como `postgres`, PostgREST como `authenticated`).
- **Anular con el turno ya cerrado no reescribe su arqueo.** `void_commission_settlement` devuelve `{cash_returned, cash_locked_in_closed_shift}`: solo borra el movimiento si el turno sigue abierto. Un conteo que alguien ya firmó no se toca.

# Turnos, zona horaria y ticket promedio (`20261007150000`–`150100`)

- `close_shift` redondea contado, esperado y diferencia a 2 decimales ANTES de exigir justificación (`difference <> 0`). Cada quien ve y cierra SU turno abierto (por membresía) aunque le hayan quitado `pos`; cerrar el de otro (`p_shift_id`) exige `is_tenant_owner()` (`OWNER_REQUIRED`). `open_shift` y `register_cash_withdrawal` siguen exigiendo `pos`. Lectura de `shifts`: el dueño/admin ve todos; un trabajador, solo los de su membresía. `anon`/`authenticated` no tienen TRUNCATE/TRIGGER/REFERENCES sobre `shifts` ni `cash_movements` (TRUNCATE no pasa por RLS).
- **Ticket promedio**: `finance_overview.ticket_count` / `sales_summary.ticket_count` cuentan ventas completadas con total > 0; `sales_count` sigue siendo el conteo crudo. Un premio canjeado entero (total 0) es venta pero no ticket. Cliente: `averageTicket(billed, ticketCount)`.
- **Zona horaria del negocio**: Panel, Reportes y Gastos cortan días y meses con `fetchBusinessTimeZone()` (`business_sites.timezone`, la misma que fecha los retiros de caja; respaldo: la del navegador). Los rangos se traducen a instantes recién en `toIsoRange(range, tz)` / `monthSpanToIso(span, tz)` / `localDayStartIso(day, tz)` (`lib/tz.ts`).
- **"Este mes"** es el mes de calendario completo en Panel (`homePeriodRange`) y en Gastos (`resolveExpenseRange`); la comparación del Panel usa los días TRANSCURRIDOS (`previousPeriod(…, now, tz)`).
- **Sumas de plata en el cliente**: en centavos enteros (`sumMoney`/`addMoney`, `lib/money-sum.ts`), nunca `reduce` sobre floats.
- **Gastos** (`/dashboard/expenses`) tiene gate de servidor como Reportes: un trabajador sin `panel` es redirigido.

# Clientes, abonos y flujo de caja (`20261007110000`–`110300`)

- `customers`: `anon` no escribe; `authenticated` no escribe `credit_balance`, `haircut_count`, `haircuts_since_reward` ni `loyalty_points` (GRANT por columna — no mandes esas claves en un insert/update, PostgREST rechaza la sentencia entera). `credit_limit`/`tax_exempt` solo los cambia `is_tenant_owner()` (trigger `customers_guard_owner_fields`; al crear, un trabajador los deja en NULL/false). DELETE solo del dueño y nunca con `credit_balance <> 0` (`CLIENTE_CON_SALDO`). Los guards actúan solo cuando `current_user` es `authenticated`/`anon`: las funciones SECURITY DEFINER y los CASCADE pasan.
- **Abonos** solo por `register_customer_payment(customer, amount, notes, p_payment_method='efectivo', p_client_payment_id)`; no hay INSERT directo en `customer_payments`. Idempotente por `client_payment_id` (el modal genera uno por intento). `credito` no es un método de abono. Efectivo: el trabajador necesita turno abierto (`ABONO_SIN_TURNO`); el dueño sella su turno, o el único abierto, o ninguno.
- **Arqueo**: `current_shift`/`close_shift` devuelven `cash_in`, `cash_abonos` y `movements_by_kind`; esperado = base + `cash_in` + `cash_abonos` − `withdrawals_total`. `shiftCashBreakdown` (`lib/pos-shift-close.ts`) arma las filas del cierre y cuadra por construcción.
- **Flujo de caja = CAJA, no devengado**: `finance_overview` y `aggregateOverview` cuentan lo cobrado al vender (`sale_payments` sin `credito`; ventas viejas sin filas de pago: total salvo fiadas) + abonos por `created_at` + facturas pagadas por `paid_at`. `revenue` = `sales_income` + `abonos_income` + `invoices_income`; `sales_billed` y `credit_issued` (lo fiado del período) van aparte. "Ventas hoy" del Panel sigue siendo lo facturado.
- `invoices.paid_at` lo escribe el trigger `invoices_stamp_paid_at` (al pasar a `paid`; NULL al salir). Compras y facturas se fechan por `paid_at` en Finanzas, Reportes y Gastos, nunca por `issue_date`.

# Compras: todo pasa por RPC (`20261007120000`–`120200`)

- Alta/edición = `save_purchase_invoice(id|null, header, items)`: una transacción con la factura bloqueada (cabecera, líneas, stock, historial, totales y último costo). La base calcula `line_total` y los totales; lo que mande el cliente se ignora. Fallback PGRST202 al camino viejo.
- **El IVA va sobre (subtotal − descuento)**: `purchaseTotalsOf` (`lib/purchase-totals.ts`) espeja `public.purchase_totals`; si cambia una, cambia la otra. Al editar se conserva el `tax_rate` guardado (`purchaseTaxRateFor`) salvo cambio explícito.
- Recibir un pedido = `receive_purchase_order`: bloquea el pedido, exige `issued` sin factura y es idempotente (`already_received`). El `unit_price` de un pedido es `purchase_price` (costo de CAJA si `units_per_package > 1`) y la cantidad está en unidades: la compra se arma en cajas + sueltas. Las líneas sin producto se omiten.
- **Último costo**: guardar o recibir una compra pone en `products.purchase_price` el costo de la compra no anulada más reciente (`issue_date`, luego `created_at`) con costo > 0, en la unidad del producto (caja si `units_per_package > 1`). Anular no lo toca. Lo escribe `sync_products_last_cost` con el flag `app.syncing_purchase_cost`, que `products_guard_edit` respeta solo si lo único que cambia es el costo.
- **Guards** (`invoices_guard_purchase_write`, `invoice_items_guard_purchase_write`), solo para `type='compra'` y escrituras desde el cliente (`current_user` authenticated/anon): no se escriben líneas directo, no se borra una compra con líneas, no se cambia el tipo, nadie reactiva una anulada, y anular exige el flag `app.cancelling_purchase` que solo levanta `cancel_purchase_invoice`. Si el cliente toca los campos de plata, la base los recalcula desde las líneas. Factura/cotización no se tocan.
- **Pedidos (`20261007160000`–`160300`)**: alta/edición = `save_purchase_order(id|null, header, items)` (una transacción; editar exige `draft`; con `status='issued'` guarda y emite; fallback PGRST202). Guards `guard_purchase_order_write` / `guard_purchase_order_items_write` (mismo patrón `current_user`): desde el cliente solo draft→issued|cancelled e issued→completed|cancelled; `received` + `invoice_id` los pone SOLO `receive_purchase_order`; received/completed/cancelled son finales (`PEDIDO_CERRADO`); las líneas solo cambian en `draft` (`PEDIDO_NO_EDITABLE`); un pedido recibido no se borra.
- **Numeración de pedidos**: `purchase_order_counters` (una fila por negocio, `ON CONFLICT DO UPDATE` la bloquea); nada de `max()+1`.
- **Recibir** acepta `p_status` (`paid`/`pending`) y `p_tax_rate` (default `paid`/0; la UI propone la tasa configurada). El valor del pedido en pantalla sale de `orderTotal` (`lib/purchase-order-lines.ts`): cajas a precio de caja + sueltas a `round(caja/u, 2)`, espejo de `receive_purchase_order`; si cambia uno, cambia el otro.
- **Stock congelado**: `invoice_items.stock_qty_applied` guarda lo que cada línea de compra sumó al stock (según el `tracks_stock` AL GUARDAR). Editar/anular revierten eso, no lo que diga el `tracks_stock` de hoy. NULL = legado → regla vieja.

# Catálogo: un servicio vive SOLO en `services`

A service is one row in `public.services` — never also a `products` row. It used to be both, matched by name with `ilike`, and the sync was one-way and swallowed by empty `catch {}`; measured in production before `20260815000000_services_single_source_of_truth.sql`, **zero** pairs were actually in sync. `services` wins because it holds `duration_minutes`/`description` and is the FK target of `appointments.service_id`, `sale_items.service_id`, and the public booking site.

- **Never write a product with `unit = 'Servicio'`.** The constraint `products_unit_is_not_service` rejects it. Rows predating the migration survive only because `sale_items.product_id` references them; `SERVICE_UNIT`/`isServiceItem` exist to keep those out of every products query (`fetchProducts`, `fetchCatalog`, the Pedidos query).
- **One screen, one form.** `/dashboard/inventory` is the catalog (`lib/catalog.ts` merges both tables in memory) and `/dashboard/inventory/product` is the only creation form: `?id=` edits a product, `?serviceId=` edits a service, `?type=servicio` opens the Servicio tab. `/dashboard/services` is a permanent redirect; nav item `inventory` is named "Productos y servicios" and shows for either the `inventory` or `services` module.
- **Services are archived, never deleted.** `sale_items.service_id` and `appointments.service_id` are `ON DELETE SET NULL`, so deleting detaches history instead of removing the service. Use `setServiceStatus`.
- Writing to `services` requires `worker_can('services')`, not `inventory_edit` — the two halves of the catalog have separate write permissions.
- **A school lesson plan owns its service by default.** `components/school/PlanForm.tsx` creates a `services` row (same name/price, via `useServicesStore().addService`) for every NEW plan, then points `school_lesson_plans.service_id` at it — "Usar un servicio existente" is the escape hatch to link one already in the catalog instead. This exists because with an empty catalog the old service picker had nothing to select, and plan creation dead-ended silently (T9). `school_lesson_plans` itself has no price column — the service carries the price, and `school_enrollments.plan_price` freezes it at enrollment time.

# Subscription billing (ePayco)

Two products in one: the **Smart Checkout** (hosted payment) and the **ApiFy** REST API. `services/epayco.service.ts` is the only place that talks to either; the pure protocol logic (signature, status maps, session payload) lives in `services/epayco-protocol.ts` and is tested without network in `tests/epayco-protocol.test.ts`.

**Verify against the API, not the prose.** ePayco's narrative docs, its Node SDK and its live API contradict each other. The authoritative contract is the Postman collection behind `https://api.epayco.co` (fetch `https://api.epayco.co/api/collections/5378697/T1DtfG34`). The `epayco-sdk-node` package describes an older generation — do not use it as an architecture reference.

- **Base**: `https://apify.epayco.co`. There is **no sandbox host**: the same host serves test and production; the mode comes from the keys plus the `test` flag passed to the browser checkout. `EPAYCO_MODE` defaults to `test` so an unconfigured deploy cannot charge real money.
- **Auth is two-step**: `POST /login` with `Authorization: Basic base64(PUBLIC_KEY:PRIVATE_KEY)` returns a short-lived JWT for `Authorization: Bearer` on everything else. **`/login` returns HTTP 200 even when it fails**, with `{"error": …}` instead of `{"token": …}` — check for the token explicitly. The JWT's lifetime **varies** (observed 20 min, documented 1 h), so parse its `exp` rather than assuming a TTL.
- **Four secrets, not two**: `EPAYCO_PUBLIC_KEY`/`EPAYCO_PRIVATE_KEY` authenticate the API; `EPAYCO_P_CUST_ID_CLIENTE`/`EPAYCO_P_KEY` sign the confirmation. They come from two different blocks of the ePayco dashboard. Cross-check: the JWT's `sub` must equal `P_CUST_ID_CLIENTE`, otherwise the keys are from different accounts and the webhook signature will never validate.
- **Hosted checkout**: `POST /payment/session/create` returns a `sessionId` — **not a URL**. Only `https://checkout.epayco.co/checkout-v2.js` can open it, so `/api/billing/subscribe` returns the sessionId and `services/epayco-checkout.service.ts` loads the script on demand. `type: "standard"` redirects and returns to the `response` URL; `onpage` renders a modal (its `configure()` handler exposes `onResponse`/`onClosed`/`onErrors`). No card data ever reaches Ventex.
- **ePayco rejects the hostname `localhost`** in `response`/`confirmation` with `property Response is not a valid URL`. It is the name, not the scheme — plain `http://` on a public domain is fine, and `127.0.0.1` works. `publicUrlBase()` rewrites it; without that, checkout cannot be exercised in development.
- **The confirmation** POSTs ~30 `x_` fields signed as `sha256(p_cust_id_cliente ^ p_key ^ x_ref_payco ^ x_transaction_id ^ x_amount ^ x_currency_code)` with a literal `^`. The values are hashed **exactly as received** — reformatting `x_amount` from `"20000.00"` breaks the hash. The signature does **not** cover the status, and does not prove the amount belongs to *this* order: `applyObservationToOrder` cross-checks amount and currency against the row. The status code arrives as `x_cod_response` **or** `x_cod_transaction_state` — read it through `confirmationCode()`.
- **Two status vocabularies.** The confirmation speaks numeric codes (1 Aceptada, 2 Rechazada, 3 Pendiente, 4 Fallida, 6 Reversada, 7 Retenido, 8 Iniciada, 9 Caducada, 10 Abandonada, 11 Cancelada — there is no 5); the transaction listing speaks text (`"Aceptada"`, `"Cancelada"`). Hence `confirmationOutcome()` and `outcomeFromStatusText()` are separate. Both fail closed: anything unknown is `pending`, never credited. The published status list is incomplete — sandbox produced an undocumented `"pre-procesada"`.
- **Polling is the primary reconciliation path, not the webhook.** `x_ref_payco` only exists once someone pays, so `findTransactionByReference()` queries `POST /transaction` filtered by `filter.referenceClient` = our `billing_orders.order_id` (sent as `invoice` when the session is created). This resolves a payment even if no notification ever arrives. Note the collection declares that endpoint as `GET` with a body, which `fetch` cannot send — **use POST**.
- **The `ref_payco` query param on the return URL is useless for lookup.** It is not the `referencePayco`: neither `filter.referencePayco` nor `POST /payment/transaction` resolves it ("Transacción no existe"). Reconcile by `referenceClient` only.
- **`apply_billing_charge(order)`**: takes the order id and derives the owner from the row it just marked paid. A row with no `user_id` is a guest checkout: marked paid without activating a licence, and `claim_guest_orders(email)` activates it when the visitor registers with that email. The returned `guest` flag — not the caller's copy of the row — decides whether the guest email goes out. A `client_licenses` row always wins over online billing.
- **`/api/billing/recurring` is a documented NO-OP.** ePayco exposes no recurring charge without tokenizing a card (`POST /token/card` takes the raw PAN, expiry and CVC), which would add a PCI surface Ventex does not have. Since no order stores a reusable token, `sync_billing_schedule` leaves `billing_recurring` false everywhere, so there is nobody to charge. The route still **requires `CRON_SECRET`** and returns 503 without it — do **not** re-add an `x-vercel-cron` header bypass: that header is forgeable.
- **Buying and renewing always go through the checkout — never WhatsApp.** WhatsApp is support-only (`Soporte` button + the "¿Dudas?" link under the landing prices). # Primitivas de UI (`components/ui/`)

Para pantallas NUEVAS o al tocar una existente; no hace falta migrar todo de una vez.

- **`Modal`** (`open`, `onClose`, `title`, `size`, `footer`, `dismissible`, `closeOnEscape`, `initialFocusRef`): todo diálogo con contenido propio. Va sobre `<dialog>.showModal()`: foco atrapado, Escape, scroll del fondo bloqueado y `aria-labelledby` vienen solos — no escribas otro `fixed inset-0` a mano. Es controlado: Escape/fondo/X solo PIDEN cierre (`onClose`); si estás guardando, ignorá el pedido. Va en la *top layer* y el resto de la página queda `inert`: un desplegable portaleado tiene que usar `usePortalContainer()` (`portal-container.ts`), como ya hace `Select`, o se abre debajo del fondo y no recibe clics.
- **`Modal` — `placement`**: `center` (por defecto), `sheet` (hoja inferior en el celular, tarjeta desde `sm`) o `right` (cajón lateral a todo el alto). El diálogo lleva `print:hidden`: al imprimir con un modal abierto sale la página, así que los modales que imprimen SU propio contenido (comprobante de comisión) siguen a mano. Un overlay hecho a mano que se abra DESDE un `Modal` tiene que renderizarse dentro de su árbol (queda dentro del `<dialog>`); como hermano, queda inerte debajo del fondo.
- **Cambios sin guardar al salir por el menú**: el formulario llama `useUnsavedChangesGuard(dirty)` (`lib/unsaved-changes.ts`) y el shell (menú lateral, encabezado, cajón móvil, paleta Ctrl+K) pregunta con `useConfirm` antes de navegar. No reemplaza el `beforeunload` de cada formulario (recargar/cerrar pestaña) ni su propio "Volver".
- **`ExportButtons` / `OpenOnNewParam`** viven en `components/ui/` (exportar CSV/Excel; abrir el modal de alta con `?new=1` o aplicar `?filtro=`).
- **`ConfirmDialog` / `useConfirm`**: toda pregunta sí/no antes de una acción (nunca `window.confirm`). Usa `Modal` por dentro; el foco arranca en Cancelar.
- **`Switch`** (`checked`, `onCheckedChange`, y `label` o `aria-labelledby` o `aria-label`): todo interruptor encendido/apagado. `role="switch"` + `aria-checked`, área táctil de 40px. No más `<input type="checkbox" class="sr-only peer">` con la pista dibujada a mano.
- **`Button` / `IconButton`**: `variant` primary/secondary/danger/ghost, `size`, `loading` (deshabilita + spinner + `aria-busy`). `type="button"` por defecto: para enviar un formulario, `type="submit"` explícito. `IconButton` exige `aria-label` y mide 40×40.
- Animaciones de entrada: `animate-in fade-in zoom-in-95 slide-in-from-*` vienen de `tw-animate-css` (importado en `app/globals.css`), y se apagan solas con `prefers-reduced-motion`.

# Conventions

- **UI is entirely in Spanish** — keep new copy consistent.
- **La copy de UI va en español de Colombia con TUTEO** (tú: "elige", "puedes", "escríbenos"), nunca voseo ("elegí", "podés", "escribinos"). Aplica también a mensajes de error que ve el usuario y a los textos por defecto de WhatsApp.
- **Montos en pantalla: `useFormatMoney()`** (`lib/useMoney.ts`), que formatea en la moneda del negocio (`settings.currency`, cargada una vez por `DashboardShell` vía `ensureSettings()`, con fallback a COP). Helpers puros reciben la moneda o un `MoneyFormatter` por parámetro. Quedan en COP fijo a propósito: precios de planes de Ventex (Mi Plan, landing, checkout ePayco, `/admin`) y el sitio público `[slug]` (su RPC no expone la moneda).
- **TypeScript path alias**: `@/*` → repo root.
- **Tailwind CSS v4**: no `tailwind.config.*`. Theme tokens defined in `app/globals.css` via `@theme inline`. Use token classes (`bg-surface-container`, `text-on-surface`, etc.) — do not hardcode hex values.
- **Theming**: `:root` = light, `:root[data-theme="dark"]` / `.dark` = dark. Synchronous inline script in `app/layout.tsx` applies saved theme before hydration (no saved choice → follows `prefers-color-scheme`; dark when the system has no preference). `components/ThemeProvider.tsx` manages toggling via `useTheme()` hook.
- **Business-type gating**: which modules/nav items a tenant sees is computed from `config/business.ts` (`REGISTRABLE_BUSINESS_TYPES`, `visibleNavItems`, `workerNavItems`) — single source of truth; don't duplicate that logic per page.
